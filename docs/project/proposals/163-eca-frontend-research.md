# 163 — ECA front-end: research and standards

**Status:** research (feeds `163-eca-frontend-proposal.md`)
**Date:** 2026-11-24
**Scope:** the default public front-end for the NV oOS **ECA toolkit** (WordPress or
Laravel), generated by the Astro forge from the current eca.directory site.

The question this file answers: *what does the market actually ship for a school
co-curricular / ECA catalogue, and which standards bind the build?* Everything
below is either a competitor capability, a published UX finding, or a W3C/IETF/
schema.org contract the implementation must honour.

---

## 1. What the ECA toolkit already models (the source of truth)

Read from `addons/pro/` (not the live site — the live site uses almost none of it):

| Layer | Facts |
|---|---|
| CPT | `mcp_ai_eca` (rewrite `/eca`, archive on, REST on), `mcp_ai_student` (rewrite `/student`) |
| Taxonomy | `mcp_ai_eca_category` (hierarchical, REST on, rewrite `/eca-category`); 8 defaults: `sports`, `arts-music`, `academic`, `health-wellness`, `technology`, `community`, `leadership`, `other` |
| Meta (`Pro_CPT_Meta_Schema`) | `_eca_code`, `_eca_type`, `_eca_day`, `_eca_start_time`, `_eca_end_time`, `_eca_venue`, `_eca_max_students`, `_eca_year_groups`, `_eca_teachers`, `_eca_is_paid`, `_eca_cost`, `_eca_cost_period`, `_eca_requires_audition`, `_eca_booking_type`, `_eca_status`, `_eca_google_course_id`, `_eca_classroom_sync` — **the live value sets differ from the schema; see below** |
| Enrolments DB | `status` ∈ `enrolled`, `waitlisted`, `withdrawn`, `completed`; per-tenant rows |
| Tools (`tools/eca-management/`) | `list_ecas` (filters: **day, year_group, venue, status, search**; sort: name/day/created/type; paginated), `get_eca`, `create/update/delete_eca`, `set_eca_schedule`, `get_eca_timetable` (**view_type**: student/teacher/venue/year_group; `week_of`; `include_conflicts`), `check_eca_conflicts`, `enroll_student_eca`, `withdraw_student_eca`, `manage_eca_waitlist`, `manage_eca_term`, `mark_eca_attendance`, `generate_eca_participation_report`, `sync_ecas_from_isams` / `from_socs`, `isams_query` |
| Sync | Google Classroom (course + roster + announcements), iSAMS, SOCS |

**Implication.** The *canonical facet model is the toolkit's own filter vocabulary*
(day · year group · venue · status · category · free-text), and the canonical
*schedule model* is weekday + start + end (+ term). The front-end must be built on
that vocabulary, not on an invented one.

**What the live site actually has (verified 2026-11-24, 105 records).**

- **`_eca_*` meta IS exposed in REST** — but only when `_fields` names `meta`.
  An earlier reading ("`meta` carries only Kadence keys") came from a request
  that omitted it. All 18 toolkit keys plus `_tenant_type`/`_tenant_id` return.
  This removes the need for a dedicated projection endpoint (P6) to *read* the
  data; it still needs one to *shape* it for Laravel parity.
- **The live enums differ from the schema**, so the format must accept unknown
  values rather than validate against a closed list:

  | Field | Schema says | Live values (count of 105) |
  |---|---|---|
  | `_eca_type` | — | `club` 42, `activity` 21, `sport_academy` 15, `society` 14, `sport_squad` 13 |
  | `_eca_booking_type` | `open`/`audition`/`invite_only` | `preference_based` 48, `first_come_first_served` 46, `preselected` 6, `signup` 5 |
  | `_eca_cost_period` | `per_term`/`per_year`/`one_time` | `""`, `term`, `year`, **`month`** |
  | `_eca_start_time` | `HH:MM` | `2:45 PM` (103/105) |
  | `_eca_year_groups` | array | **empty for 105/105** |
  | `_eca_is_paid` | bool | **`null` for 105/105** |
  | `_eca_max_students` | int | `0` (unset) for 78/105 |
  | `_eca_code` | — | `ECA-007` … but also bare `30`, `10` |

- **What that forced on the format** (all implemented and tested in
  `examples/nvoos-astro-forge/lib/eca.ts`): `_eca_cost > 0` is the paid signal,
  not `_eca_is_paid`; year groups come from the labelled prose block
  (`Year Groups: Year 10 to Year 13`), free prose (`Years 7-13`) or the title
  shorthand (`Sailing (Y4-6 Saturday Beginner)`); `_eca_max_students: 0` means
  "not published", never "no places".
- **Stage is derivable for 93/105 (89 %)** by chaining year-range → title token
  → slug prefix; the remaining 12 have no signal and stay browseable under an
  explicit "all stages" bucket. Splitting on `SS` alone would have lost two
  thirds of the catalogue (only 31 titles carry it).
- **The taxonomy is sparse**: 44/105 records carry no category. `_eca_type` is
  complete (105/105), so **type — not category — is the primary browse facet**,
  with category as a secondary facet that can be empty.
- **One record (11155) publishes an internal import note** — `[Note: the
  remainder of this entry in the source booklet (day, time, venue, capacity and
  teacher-in-charge) was not readable in the supplied PDF and still needs to be
  confirmed.]` — which the normaliser strips and logs as an inference.

### The school's own sources (verified 2026-11-24)

The Michaelmas 2026-27 booklet (Senior School) plus
`britishschool.lk/admissions/term-dates` settle the facts the WP records cannot
express — and they resolve proposal decision **D1**:

| Fact | Value | Consequence for the format |
|---|---|---|
| Booking platform | SOCS — `socscms.com/login/29451/parent` | **D1 resolved**: `booking.mode: 'external'` with ONE URL for every activity. SOCS exposes a parent login and no per-activity deep link, so a per-activity `urlTemplate` cannot exist here. |
| Booking window | opens Wed 26 Aug 2026 07:00 · closes Sat 29 Aug 23:59 · allocations from Wed 2 Sep | A first-class UI state (`bookingState()` → before/open/closed/allocations/running), not a footnote. Parents plan around this window, so the catalogue states it. |
| Term dates | term opens 24 Aug · **ECAs begin 7 Sep** · end **15 Dec 2026** | `terms[].start` is the first day an ACTIVITY can run, not the term opening — a series that starts on 24 Aug would be three weeks wrong. |
| Half-term | 19–23 Oct 2026 | One `EXDATE` per meeting day. Without it every one of the 103 calendar feeds shows a club meeting during half-term. |
| Schedule rows | "Wednesday & Thursday" | `schedule.days[]`, not a single day — the booklet's own tables carry two-day rows, and the WP meta kept only one. |
| External fees | "paid directly to the individual provider" | `booking.note`, rendered on paid activities. |
| Contacts | ECA coordinator, IT support, per-sport leads | The info/help pages (P5) carry these verbatim. |

**Implication.** The format is **optional-field-first with explicit
provenance**, but "thin" is field-specific, not dataset-wide: schedule, venue,
stage and price are 89–99 % derivable, while year groups, capacity and the
taxonomy are mostly absent. Never render a fact the source did not state (no
invented capacity, no invented times), and never let a missing field remove a
record from the catalogue.

## 2. What the market ships (competitor capability matrix)

| Capability | SOCS Co-curricular | SchoolsBuddy | iSAMS Activities Manager | eca.directory (live) |
|---|---|---|---|---|
| Activity catalogue | ✓ | ✓ | ✓ (categories + subcategories per activity) | ✓ (day grids) |
| Categories / strands | ✓ | ✓ | ✓ arbitrary taxonomy | ✓ 8 |
| Sign-up models | first-come, invitation, **preference-based auto-allocation** | same three + **flexible mid-term join requests** | ✓ | none (static list) |
| Capacity / waitlist | ✓ oversubscription algorithm | ✓ auto-allocation | ✓ | no |
| Payments | ✓ billing | ✓ online payments | via portal | links to WooCommerce |
| Calendar | ✓ per role, iCal + XML feeds | ✓ auto-filled personal diary | ✓ | none |
| Conflict detection | ✓ timetable overlaps | ✓ allocation-time | ✓ | no |
| Attendance / registers | ✓ | ✓ | ✓ | no |
| Safeguarding / medical | ✓ | ✓ | ✓ | no |
| Per-role views | staff / parent / pupil | same + transport | staff / pupil | public only |
| Term rollover | ✓ | ✓ | ✓ | no |
| MIS integration | iSAMS, portals | PowerSchool, ManageBac | native | none |

Sources: [SOCS Co-curricular](https://socs.tech/our-tools/socs-co-curricular),
[SchoolsBuddy Activities](https://www.schoolsbuddy.com/activities-event-management),
[iSAMS Activities Manager](https://www.isams.com/platform/modules/activities-manager/).

**What to copy**

1. **Three sign-up modes are table stakes** (`open`, `preference`/audition,
   `invite_only`) — the toolkit already has `booking_type`; the UI must *name* the
   mode on the card (“Sign up”, “Register interest”, “Invitation only”). Note the
   live site already runs **four** values (`preference_based`,
   `first_come_first_served`, `preselected`, `signup`), so the UI labels a mode
   rather than assuming a closed set.
2. **Capacity is a first-class UI state** (open → “12 of 20 places”, waitlist →
   “Join waitlist”, closed → “Full”). SOCS/SchoolsBuddy both surface it on the
   list, not only the detail page.
3. **Per-role calendars** (parent/pupil/staff) and **iCal export** are expected.
4. **Mid-term join** (“request to join”) matters for a public site — an activity
   that started in week 1 still needs a way in.
5. **Term rollover** means the catalogue is *term-scoped*; the UI needs a term
   selector and a “this term / next term” distinction.

**What to avoid**

1. **Do not build a login wall for browsing.** Every competitor sells the
   *management* side; the public directory must stay readable (SEO + no-JS).
2. **Do not invent availability.** Where capacity is unknown (the current data),
   say nothing rather than “spaces available”.
3. **Do not use colour alone** for categories (see §4).
4. **Do not put the calendar behind JS only** — an agenda list is the accessible
   baseline.

## 3. Faceted filtering — what the research says

Baymard's benchmark is the strongest current evidence base: **78 % of mobile
e-commerce sites have a poor-to-mediocre filtering experience** (2025 benchmark,
cited by [wisepim](https://wisepim.com/blog/ecommerce-product-filters-ux-best-practices)),
and filters are one of the top-5 UX failures overall
([Baymard, filter UI best practices](https://baymard.com/blog/ecommerce-filter-ui)).

Rules that apply directly to an activity catalogue:

1. **Facets belong on the list page, not a separate “advanced search”.**
   Category-specific facets beat generic ones —
   [Baymard navigation research](https://baymard.com/research-articles/ecommerce-navigation-best-practice).
2. **Counts next to every value** (“Sports (26)”) so a tap is predictable, and
   long lists get their own search box / “show more”
   ([Gladly faceted search](https://www.gladly.ai/blog/faceted-search-best-practices/)).
3. **Mobile is a drawer, desktop is a sidebar.** The mobile trigger is sticky and
   shows the active count.
4. **URL state is mandatory** — shareable, back-button-safe, and indexable
   ([BTNG filter patterns](https://www.btng.studio/articles/top-ecommerce-ux-filter-design-patterns-practical-tips-for-2025/)).
   Rule: *every filter is a query parameter; no filter state lives only in JS.*
5. **Active filters are chips** with individual “×” and a “clear all”; result count
   is announced (`aria-live="polite"`).
6. **Empty state is a feature**: show what was filtered, offer “clear all” and the
   nearest non-empty combination.
7. **Never reorder facet values between renders** — users lose their place.

For an ECA catalogue the facet ORDER follows the user's mental model, not the
database: **Day → Stage → Year group → Category → Time of day → Availability →
Price**.

## 4. Accessibility — WCAG 2.2 AA is the floor

Canonical spec: [WCAG 2.2](https://www.w3.org/TR/WCAG22/). The criteria that this
UI actually exercises:

| SC | Requirement | Where it bites here |
|---|---|---|
| 1.4.3 / 1.4.11 Contrast | 4.5:1 text, 3:1 UI | category chips, availability badges, focus rings |
| 1.4.1 Use of Colour | never colour alone | category colour **plus** label/icon |
| 2.4.11 Focus Not Obscured (Min) | focused item not hidden | sticky header + sticky filter bar |
| 2.4.7 Focus Visible | always visible | filter chips, cards, calendar cells |
| 2.5.8 Target Size (Min) | ≥ 24×24 CSS px | filter chips, calendar day cells, “×” buttons |
| 3.2.6 Consistent Help | same help affordance in the same place | `/help` + `/contact` in the footer **and** the filter drawer |
| 3.3.7 Redundant Entry | don't re-ask | shortlist + filter state survive navigation |
| 2.2.2 Pause/Stop/Hide | motion can be paused | any card entry animation |
| 2.3.3 Animation from Interactions | respect `prefers-reduced-motion` | card/marker motion |

Calendar-specific pattern guidance: [UX Patterns — Calendar
View](https://uxpatterns.dev/patterns/data-display/calendar) (grid semantics,
keyboard model, announced period changes). Colour-coding must be paired with an
icon/pattern label ([Muzli calendar guidance](https://muz.li/inspiration/calendar/)):

> colour communicates category, duration and status — but must be backed by
> pattern or icon differentiation in high-density views.

## 5. Calendar and calendar export

- **Views**: Agenda (default ≤ 767 px), Week, Month. Multiple view toggles are the
  consistent recommendation
  ([Page Flows](https://pageflows.com/resources/exploring-calendar-design/),
  [Bricx](https://bricxlabs.com/blogs/calendar-ui-examples)).
- **Agenda is the no-JS baseline**: the activity list grouped by date is HTML; the
  month/week grids are progressive enhancement.
- **Export**: iCalendar is [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545); a
  weekly activity is `RRULE:FREQ=WEEKLY;BYDAY=TU;UNTIL=<term end>` with a stable
  `UID` (`<eca-code>@<host>`), `TZID` from the site profile, and a `webcal://`
  one-click link. Per-facet feeds (`/feeds/<stage>.ics`) are cheap and expected
  (SOCS advertises iCal/XML).
- **Term scope**: a weekly rule must be clipped by the term calendar, or an
  exported feed advertises sessions during holidays.

## 6. Structured data — be eligible, be honest

- Google's **course info / course list** markup uses schema.org `Course` +
  `CourseInstance`; the policy is explicit that the feature targets course
  listings, and that **“public events unrelated to a structured curriculum” are
  ineligible** ([Google course docs](https://developers.google.com/search/docs/appearance/structured-data/course),
  [2023 course-info announcement](https://developers.google.com/search/blog/2023/11/new-course-info-markup)).
- Practical mapping for an ECA:
  - **Activity detail** → `Course` (name, description, `provider`) +
    `hasCourseInstance` → `CourseInstance` (`courseMode`, `startDate`/`endDate`
    from the term, `location`).
  - **Dated session / term event** → `Event` with `eventSchedule`
    (`Schedule` + `byDay` + `startTime`/`endTime`, `repeatFrequency: P1W`).
  - **Programme pages** (Junior / Senior) → `EducationalOccupationalProgram` is
    defensible; `ItemList` for the catalogue.
  - **Never** `aggregateRating` without real reviews — fabricated ratings violate
    Google's structured-data policies
    ([schemavalidator note](https://schemavalidator.org/guides/course-schema-markup)).
  - **Never** `FAQPage` / `HowTo` — Google removed the FAQ rich result (2026-05-07)
    and HowTo (2023). The repo already pins this rule (Proposal 136).
- `BreadcrumbList` on every level; `Organization` (the school) once per page.

## 7. Performance and build shape

- The catalogue is **static-first**: every activity is a real page (SEO, no-JS,
  cheap CDN). Filtering is client-side over an embedded index (≈105–2 000 rows);
  beyond that, paginate or move to the managed/SSR tier.
- Budgets (the forge already gates text/geometry/colour; these are the new ones):
  LCP ≤ 2.0 s on a throttled 4G profile, CLS ≤ 0.05, INP ≤ 200 ms, catalogue
  island JS ≤ 40 KB gzip, zero layout shift from the filter drawer.
- Images: `SmartImage` (same-host, AVIF/WebP, explicit dimensions), hero
  `fetchpriority="high"`, everything below the fold lazy.
- Search index: a tiny pre-built JSON (title, slug, category, day, year groups,
  keywords) — **no server required**; when the site is SSR/managed, the same
  shape comes from `nvoos-eca/v1/activities?q=`.

## 8. What this means for the forge (design constraints, not features)

1. The front-end must be **host-agnostic**: WordPress (`wp/v2` + ECA meta) or
   Laravel (`nvoos-eca/v1`) behind the same normaliser.
2. The **format is the product**: a versioned JSON contract (`nvoos-eca/v1`) with
   optional fields and an `inferred` provenance list.
3. Thin data is the *default* case, not an edge case: the normaliser must derive
   day/stage/price from prose and mark what it inferred.
4. Facets must be data (counts, ordering) not hard-coded UI.
5. The calendar is a view over the same normalised records — never a second model.
