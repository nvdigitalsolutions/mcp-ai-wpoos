## 1. Scope

Phase P5 enforces the "one tool, one responsibility" guideline from [§2.1](../UNIX_THEORY_COMPLIANCE_ENHANCEMENT_PROPOSAL.md#21-one-tool-one-responsibility) of the proposal:

> Any tool whose `action` parameter has more than 4 values must be decomposed into focused sub-tools during the next major refactor cycle.

This audit was generated by a deterministic scan over `includes/tools/class-wp-mcp-ai-tool-*.php` (Base) and `addons/pro/includes/tools/**/class-wp-mcp-ai-tool-*.php` (Pro), matching every JSON-Schema `enum` array attached to a parameter whose key is `action`, `operation`, `mode`, `verb`, `op`, `command`, or `task`. The complete reproduction script lives in [§4 Methodology](#4-methodology).

**Why a tiering pass instead of a blanket "decompose everything"?**

The proposal's guideline is intentionally numeric (> 4) but the real cost of a multi-action dispatcher depends on the *cohesion* of those actions:

- A CRUD cluster (`create / read / update / list / delete`) is a single resource lifecycle. Decomposing it into five separate tool classes balloons the registry without improving LLM accuracy — the model already understands CRUD as a single concept and picks the verb with high reliability.
- A multi-domain dispatcher (`get_posts | get_wc_orders | get_wc_products | …`) is a token-tax on every LLM call and a genuine drag on tool-call accuracy because each verb is conceptually unrelated.
- An operationally-cohesive set (matrix add/subtract/multiply/…) is mathematically one tool with N forms; decomposing produces nine near-identical schemas with no accuracy gain.

Each candidate is therefore classified into one of three tiers:

| Tier | Disposition | Rationale |
|------|-------------|-----------|
| **A — Decompose** | Open a per-tool decomposition ticket in Part 2 | The actions span unrelated domains; the LLM benefits from focused schemas |
| **B — Cohesive subsystem** | Keep as-is; document the rationale | The actions are operationally cohesive (one mathematical / domain subsystem) |
| **C — CRUD-canonical** | Keep, but pin enum at ≤ 5 (no growth) | The actions form a single resource lifecycle; further growth must split |

Tier-B tools **must remain capped at their current enum size**. Any new operation pushes the tool into reconsideration under the next P5 audit.

### Tier C — CRUD-canonical (20 tools; keep, but pin at ≤ 5)

The remaining 20 tools all follow the create/read/update/list/delete shape (sometimes with one domain-specific verb like `transition`, `promote`, `schedule`, `search`). The proposal's threshold of **> 4** matches "more than CRUD," so a strict reading would force decomposition. But:

1. CRUD is a single resource lifecycle: the model picks the verb correctly from the first prompt token in nearly all observed cases.
2. The five verbs share input validation (the same resource id / payload shape).
3. Decomposing them would multiply the registry size by ~5× for zero LLM-accuracy benefit.

**Policy:** Tier-C tools are **permitted at exactly 5 verbs** when those verbs form a CRUD lifecycle. The audit pins them at their current size — any sixth verb triggers a forced decomposition unless re-classified as Tier B. This is the action-split policy as implemented in practice.

## 4. Methodology

The candidate list was generated by the following reproducible scan:

```python
# Roughly: walk every tool class file, find every JSON-Schema enum array
# attached to a parameter named one of {action, operation, mode, verb, op, command, task},
# and report cases where len(enum) > 4.
import os, re, glob
files = (
    glob.glob('includes/tools/class-wp-mcp-ai-tool-*.php') +
    glob.glob('addons/pro/includes/tools/**/class-wp-mcp-ai-tool-*.php', recursive=True)
)
for f in files:
    content = open(f).read()
    for m in re.finditer(
        r"['\"](action|operation|mode|verb|op|command|task)['\"]\s*=>\s*array\("
        r"(?:[^()]|\([^()]*\)){0,3000}\)", content, re.DOTALL):
        em = re.search(r"['\"]enum['\"]\s*=>\s*array\(([^)]*)\)", m.group(0), re.DOTALL)
        if em:
            vals = re.findall(r"['\"]([a-zA-Z0-9_\-]+)['\"]", em.group(1))
            if len(vals) > 4:
                print(len(vals), f, vals)
```

Re-running this scan after each Part-2 PR should monotonically shrink the Tier-A and Tier-C-overflow row counts. Phase P5 is considered ✅ Complete when:

- Tier-A row count = 0
- Tier-C-overflow row count = 0
- All Tier-B tools remain at their May-2026 enum sizes (no growth)
