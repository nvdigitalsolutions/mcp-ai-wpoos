Conclusion: the two bugs are the same class — **state and data that exist only at runtime are being trusted to survive a build-time snapshot** (the DOM attribute across a swap; the catalog across a mirror build).

## 2. View Transitions + theme persistence — the documented pattern

**Astro docs (View Transitions guide)** — the authoritative behaviour spec:

- Scripts in `<head>` are executed **once**, on initial page load; they are not re-executed on client-side navigations. (Our boot script is a head script — hence it only runs on the homepage load.)
- `astro:after-swap` fires "immediately after the new page has replaced the old page and **before the DOM elements are painted to the screen**." The docs' own dark-mode example re-applies the theme in exactly this event: *"This avoids a flash of light mode theme after page navigation by checking and, if necessary, setting the dark mode theme before the new page is rendered."* — that is the pattern this proposal adopts verbatim.
- `data-astro-rerun` forces an inline script to re-execute after every transition, but it only applies to **non-bundled** scripts and re-running the whole boot is the wrong granularity for a state-owning script (it would re-read storage per navigation, which is harmless but redundant; the attribute set is the work). The event-listener form is the documented, idiomatic route.
- Bundled component scripts (like `ThemeToggle`'s) are re-executed on each navigation — which is why the toggle *button* keeps working on page 2 while its *state source* (the attribute) is gone.

**Corroborating community sources (all describe our exact symptom and converge on the same fix):**

- Flavio Copes, *Astro View Transitions and Dark Mode*: "the fix is to re-apply the theme on the `astro:after-swap` event" — the canonical blog write-up of this bug.
- Stack Overflow #77092920 (*Using viewtransition for dark mode in astro*): same diagnosis; the accepted pattern restores theme state on `astro:after-swap`.
- reddit r/webdev (*How do I get dark theme working when using view transition in astro?*): "use the `astro:after-swap` event listener to persist your theme when you change routes".
- kr4t3rdev/portfolio issue #13: "Astro's view-transition swap removes … the runtime `data-theme` attribute set by the inline bootstrap is wiped on every client navigation" — identical mechanism, independent confirmation.
- codeatlasdev/ui issue #265: a theme-library author hitting the same wall in the general case (library-injected script + ClientRouter); their resolution options (server-render the attribute, or `astro:before-swap`/`astro:after-swap` handler) match our design space.

**Design takeaway for us:** the storage value (not the DOM attribute) must be the source of truth — the attribute is ephemeral across swaps; the storage value is not. The boot script owns the attribute; the toggle reads the storage value. That ordering-independence is what makes the fix robust rather than incidental.

**No-FOUC reference (already partially adopted):** Starlight's boot reads a stored theme, falls back to `prefers-color-scheme`, and applies before paint — our `BaseLayout` boot is the Starlight pattern; the swap-time half is what was missing.

## 3. Dark-mode completeness: `color-scheme`

- **web.dev, *Improve dark mode default with color-scheme and a meta tag*:** "For all elements, rendering with a color scheme should cause the colors used in all browser-provided UI for the element to match with the intent of the color scheme. Examples are scroll bars, spellcheck underlines, form controls, etc." The article is the canonical statement that palette theming *alone* leaves browser chrome light.
- **MDN, `color-scheme`:** applies to "the default colors of scrollbars and other interaction UI … form controls … other browser-provided UI"; component authors must still use `prefers-color-scheme` for their own elements — i.e. `color-scheme` is a root-level complement, not a replacement for token theming.
- **webspecification.com (color-scheme spec notes):** the two practical warnings we must honour — *"Setting `color-scheme: dark` on a site that has not been audited in dark mode: form controls and scrollbars will recolour and you will discover broken contrast in production"* (→ dark-mode audit of the PLP filter form/promo field is part of P1), and the `<meta name="color-scheme">` vs root-CSS sync requirement when a site has an OS-independent switcher (→ our switcher is JS-driven; the JS `style.colorScheme` + CSS fallback cover both JS and no-JS paths).
- **modern-css.com:** the pre-`color-scheme` approach (manual per-control dark overrides) is obsolete; one root declaration replaces it.

**Design takeaway:** theme application = `data-theme` (tokens) **plus** `color-scheme` (browser UI), applied atomically in one `applyTheme()` routine.

## 4. Headless-commerce rendering model

- **1Digital, *Headless Commerce SEO: Complete Shopify Hydrogen Guide*:** "In practice, **most Hydrogen stores should default to SSR for commerce pages and reserve SSG or ISR for supporting content**." Also: **AI crawlers (GPTBot, ClaudeBot, PerplexityBot) do not execute JavaScript** — price/description/specs must be in server HTML or the AI discovery surfaces miss them. (Our SSR pages already satisfy this; the fixture-prerendered PDP is the only route that can violate freshness.)
- **1Digital, *Headless Commerce SEO Agency* (2026 list):** "Default to SSR for category and product pages where catalog data changes and crawlers must see fresh content. Use ISR (Incremental Static Regeneration) for high-traffic PDPs where inventory [changes are bounded]."
- **naturaily, *Next.js for Ecommerce*:** "Use ISR for category pages, ISR plus on-demand revalidation for product pages, and SSR for authenticated or transactional experiences (cart, checkout, account)." — maps directly onto our architecture: category PLP (cached SSR) · PDP (cached SSR + on-demand invalidation) · cart/account (uncached SSR).
- **Patrick Stox, *Headless Ecommerce SEO*:** SSR is the safe-for-crawlers default; SSG is only safe when content is genuinely stable between deploys — the precise failure of our fixture-baked mirror.
- **beecommerce, *Headless Commerce and SEO in 2026*:** the SSG/SSR/ISR comparison — data freshness and indexability are the two axes; our live-URLs-in-sitemap + prerendered-fixture-PDPs combination fails both axes at once.
- **WPPoland, *Headless WooCommerce with Astro*:** `stale-while-revalidate=86400`-style resilience so latency spikes never surface origin errors — we already ship `stale-while-revalidate=60` on SSR pages; the PDP fix carries `swr: 600`.

**Design takeaway:** PDP = on-demand SSR + short-TTL caching + tag invalidation (Astro 7's ISR equivalent), exactly as the proposal's §3.2 prescribes.

## 5. Astro 7 route caching (the ISR-equivalent)

From the Astro 7 **Route caching** docs (feature added in `astro@7.0.0`):

- Platform-agnostic caching for on-demand pages: `cache: { provider: memoryCache() }` in config (the docs' own example pairs it with `node({ mode: 'standalone' })` — our exact adapter).
- Per-route control: `Astro.cache.set({ maxAge, swr, tags })` (pages) / `context.cache` (endpoints/middleware), guarded by `Astro.cache.enabled` (always `false` in dev and without a provider — the dev-mode-safe check the proposal wraps around PDP tags).
- Invalidation: `cache.invalidate({ tags: [...] })` (any-tag match) and `cache.invalidate({ path })` (exact-match) — the hook for the proposal's `/internal/revalidate` route.
- Declarative defaults: `routeRules` with static/dynamic/rest patterns (`/products/[...path]`), more-specific-pattern precedence; per-route `cache.set()` merges with rules (**tags accumulate**, scalars last-write-wins) — so the config-level `tags: ['products']` and the page-level `` `product-${id}` `` tag compose cleanly.
- Netlify/Vercel/Cloudflare adapters ship experimental CDN cache providers (tag/path purges at the edge); on Velocity (custom node host) the in-process provider + CDN `s-maxage` is the correct split — **Netlify's *Modern e-commerce caching with Astro* guide calls on-demand revalidation "the holy grail of page caching"**: "any given page is built only when needed, and then cached for exactly as long as its content stays valid."

**Design takeaway:** adopt `memoryCache` + routeRules + per-PDP tags; keep the HTTP `Cache-Control` header as the CDN layer; invalidation = webhook (`/internal/revalidate`) within a deploy, redeploy across deploys.

## 6. Ecosystem scan — AdminLTE.io, *15 Best Free Astro Templates (2026)*

Used as the "what does the current Astro 7 ecosystem consider table stakes" reference. The full repo-by-repo deep read — including implementation-verified theme engines (AstroPaper's `@theme inline` token bridge, astro-bento-portfolio's `appearance.ts`) and the Pro-toolkit mapping (Flowbite admin dashboard → SPA v2 consoles, Accessible Astro Starter → chat surfaces) — lives in `104-astro-ecosystem-repo-analysis.md`. Load-bearing findings:

- **Dark mode + toggle is universal** in maintained themes (AstroWind, Starlight, AstroPaper, Astroplate, ScrewFast, Accessible Astro Starter, Dante, Astro Bento Portfolio). A theme that resets on navigation is below ecosystem baseline — fixing Defect A is parity, not enhancement.
- **A11y bar:** Accessible Astro Starter ships WCAG 2.2 AA toggles for dark mode, high contrast, and reduced motion with audited form components — the reference for the `aria-pressed` + `prefers-reduced-motion` additions to our toggle.
- **Surface set:** Colorlib's premium **Shopper** storefront (the only storefront in the roundup) = product listings + category pages + PDPs + cart with quantity controls + wishlist. We have all but the wishlist; the roundup confirms the surface set is the industry norm and flags the wishlist as the known next increment (deferred — not part of this proposal).
- **Version discipline:** the roundup explicitly demotes themes stuck on old Astro majors (astroship at Astro 3 with View Transitions walled into its paid tier); the app is on Astro 7.4.4 and the forge on Astro 7 — no version debt either side.
- **The ecosystem converges on the Proposal 104 fixes:** AstroPaper's `[data-theme]` semantic-override CSS and bento's "remove-all-then-add-one" runtime theme engine are independent confirmations of the §3.1 theme module contract; ScrewFast's typed copy tables/`kind` metadata, Accessible Starter's preference-trio a11y, and Cactus's draft discipline become 104 P3-stretch items (see the repo analysis' recommendation matrix).
- **Zero-JS-by-default + islands** is the reason Astro templates score on Core Web Vitals — the storefront's existing architecture decision, validated.

## 7. Implications for the forge (Proposal 096)

- The forge templates are **static content-layer builds** today (`getStaticPaths` over `getCollection`) — correct for the static-first model, because the loader builds from the customer's **live** REST (`WP_SITE_URL`), so no fixture-data class of bug exists there. No change mandated; the SSR+cache pattern (P2) becomes the *option* for large catalogs (proposal Q4, define-only).
- The forge has **no runtime theming yet** (`tokens_apply` is build-time); when storefront parity lands, the theme runtime module (§3.1) is the unit to copy — it is authored with zero Astro-specific imports precisely so the template can take it verbatim, with the same e2e (navigate → swap → assert attribute + color-scheme + label).
- The four-point runtime contract (§3.5) converts the hard-won fixes into a **checklist future templates are scored against**, so "the foundation of the forge" is not just the tokens but the tested behaviours.
