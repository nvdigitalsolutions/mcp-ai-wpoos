## 162.1 The problem, with evidence

`FileStoreInterface` and its Laravel adapter already exist and are bound
(`NvoosServiceProvider`). Reading the implementation against its own consumers
found five defects that make it unusable as the shared file layer the document,
image and video toolkits need:

1. **`store()` never inserts a `nvoos_files` row.** It writes bytes to a disk and
   returns `StoredFile(id: crc32($path))`.
2. **Two identifier schemes on one table.** `FileUploadService` (the media
   library's writer) inserts an auto-increment row; `FileStore` invents a
   `crc32` id; `resolvePath()` only understands the auto-increment column.
3. **Consequence — the round trip is broken.** `UploadFileTool` calls `store()`
   and returns the id; `GetFileInfoTool` and `DeleteFileTool` call
   `getMetadata($id)`, which looks the id up in `nvoos_files`. No row exists, so
   `upload_file` → `get_file_info` / `delete_file` cannot work.
4. **`delete()` removes bytes only**, leaving the row, so the media library lists
   files that are gone.
5. **Every write is public.** `put(..., 'public')` is hard-coded; there is no
   visibility column and no private disk. `userCanAccess()` calls
   `Gate::allows('oos-file.access', …)`, an ability **nothing defines**, so it
   always returns false.

`crc32` is also 32 bits: two different paths can collide, so even as a synthetic
id it is not safe.

Everything the user asked for — document, image and video toolkit output, OKF
storage, Paper Store creation — would inherit these defects.

## 162.2 What WordPress does, and where we deliberately diverge

The parity source is `WP_MCP_AI_File_Service`:

| Step | WordPress |
|---|---|
| type | `wp_check_filetype()` |
| bytes | `wp_handle_upload()` → `wp-content/uploads/YYYY/MM/`, always web-readable |
| record | `wp_insert_attachment(..., 'inherit')`, `guid` = public URL |
| derivatives | `wp_generate_attachment_metadata()` — thumbnails generated in PHP at upload |
| attribution | `_mcp_ai_assistant_id` post meta |
| access | `handle_file_download()` checks `current_user_can('read_post', $assistant_id)` |

So WordPress has **no private bytes**. Access control is applied to the
*reference* while the object stays world-readable at its GUID — anyone holding
the URL reads the file.

We keep what is right and diverge where it is wrong:

| Kept | Diverged |
|---|---|
| date-sharded paths | path also carries estate and visibility |
| a row per file, attributed to an owner | id is the table's own auto-increment, never a hash |
| download is access-checked | **private bytes never get a public URL at all** |
| derivatives exist | generated by the Media Worker, not in PHP on upload (as §180 already decided) |

The divergence is recorded here rather than hidden, because it is the reason the
private path exists at all.

## 162.3 Standards applied

**OWASP File Upload Cheat Sheet** — validate the type from content, never the
`Content-Type` header; generate the filename rather than trusting one; cap length
and size; store outside the webroot where possible.

**Serving untrusted content** — send `X-Content-Type-Options: nosniff`,
`Content-Disposition` (inline only for media types that must render),
`Content-Security-Policy: default-src 'none'`, and a private cache directive.
Signed URLs and these headers both matter: AWS bakes `response-content-disposition`
into the signature so the holder cannot change it.

**Private reads** — a controller is the only place an authorisation check can
live. Signed S3 URLs replace the controller's *transport*, not its *check*; the
check stays and the last line changes when the disk becomes S3.

**Stateless cost of authorising reads in PHP** — acceptable for documents and
images at the sizes this runtime generates. Video range requests are out of scope
in this proposal (162.7).

## 162.4 Design

### One registry, one identifier

`nvoos_files` is the registry. Its `id` (auto-increment) is the only identifier
returned, stored and accepted. `crc32` is removed.

### Two visibilities

| Visibility | Disk | Read path |
|---|---|---|
| `public` | `oos.files.disks.public` (default `public` — the web-served disk) | `Storage::url()`, stable, no authorisation |
| `private` | `oos.files.disks.private` (default `local` — outside the webroot) | `GET /api/v1/files/{id}`, estate-scoped, authorisation per request |

`visibility` is a column, not derived from the disk name. A deployment that
remaps `oos.files.disks.private` to an S3 private bucket must not silently turn
private files into public ones.

### Path convention

`{tenant}/{visibility}/{Y}/{m}/{ulid}.{ext}`

- the estate is in the path, so lifecycle rules and quota reports can be scoped
  per estate later without a schema change;
- the visibility is in the path, so a misconfigured disk cannot produce a private
  object at a public-looking key;
- the extension is derived from the **sniffed** MIME type, never from the client;
- the basename is a ULID, never the client's filename. The display name is a
  column.

### One writer

`FileStore` is the only place that writes `nvoos_files` for tool output. The media
library keeps `FileUploadService` for now; both write the same table with the same
path and id conventions, and `FileUploadService` is scheduled to delegate to
`FileStore` in a follow-up (162.7) rather than being changed in the same release.

### MIME and size policy

Allowed types are grouped, and each group has its own ceiling because a video is
not an image:

| Group | Types | Default cap |
|---|---|---:|
| image | jpeg, png, gif, webp, avif | 20 MiB |
| document | pdf, txt, md, csv, json, doc(x), xls(x), ppt(x) | 25 MiB |
| video | mp4, webm, quicktime | 512 MiB |
| audio | mpeg, wav, ogg | 100 MiB |

Caps are configuration (`oos.files.limits.*`), not constants, because the right
number is deployment-specific; the defaults are the policy.

### Checksum

`sha256` of the bytes is stored. It does not deduplicate yet — two estates must not
share a mutable object — but it makes integrity checks and a future
"same file uploaded twice" report possible without re-reading the bytes.

### Delete

Bytes **and** row, in one operation, estate-scoped. A row without bytes is a
broken library entry; bytes without a row are an orphan nothing can reach.

### Access

`userCanAccess($fileId, $userId)` becomes: the row's `owner_id` matches, **or**
the app's `oos-file.access` Gate ability allows it. The ability is defined in this
release — the extension point existed but nothing fed it, which is why it always
returned false.

Estate scoping lives in the read path (the controller), not in the store, because
the store is framework-agnostic and the tenant is an app concept.

## 162.5 Decisions and rejected alternatives

| Decision | Rejected alternative, and why |
|---|---|
| a **new** interface for visibility | adding a parameter to `FileStoreInterface::store()` is a fatal error for every external implementer of the published `nvoos/core` package |
| auto-increment ids | `crc32(path)` collides and cannot be joined |
| a controller for private reads | a bare signed URL on a local disk still needs a route; the check has to exist either way, so it may as well be the only mechanism |
| visibility as a column | deriving it from the disk name makes a config change silently re-classify existing files |
| ULID basenames | keeping the client's filename is the OWASP-listed mistake; the display name belongs in the row |
| bytes + row in `delete()` | deleting only bytes leaves a phantom entry; deleting only rows leaks storage |

## 162.7 Out of scope, named

- **Video range requests.** The private controller streams whole responses. Video
  playback in a browser wants `Range` handling, and doing it badly is worse than
  not doing it. It is a follow-up with its own test (206 handling).
- **Virus scanning.** A hook point (`oos.files.scanners`) is left in the store, but
  no scanner ships.
- **Deduplication by checksum.** Deliberately not shared across estates.
- **Derivatives.** The Media Worker owns them (§180); this store does not resize.
- **Delegating `FileUploadService` to `FileStore`.** Same table and conventions
  now; one writer is the follow-up, done separately so the media library's tested
  behaviour is not bundled into this change.
- **Per-estate quotas.** The path carries the estate so a quota report is possible;
  enforcement is not built here.

## 162.8 The media slug is a column, not a derivation

`MediaController` answered `slug` with `pathinfo( $filename, PATHINFO_FILENAME )`
— the display name, minus its extension. That is fine until the display name
changes, and then it is not fine at all: tightening the registry's
`sanitize_file_name()`-style pass moved every slug with it, and a `wp/v2/media`
client that routed on a slug saw `pixel` arrive as `Pixel`. A key a client stores
must not move because a title's case changed.

WordPress never had this problem because it keeps three fields apart:

| WordPress | `nvoos_files` before §162.8 | `nvoos_files` after |
|---|---|---|
| `post_title` — what the library shows, case preserved | `filename` | `filename` (case preserved) |
| `post_name` — the slug, lowercased and unique | derived on read | `slug` (a column, unique per estate) |
| `_wp_attached_file` — where the bytes live | `path` (ULID basename) | `path` (unchanged) |

### The rules, and why each one

- **A column.** Deriving a route-adjacent key from a display field couples two
  decisions that must be free to change independently. `uniqueSlug()` writes the
  value once, at insert; readers stop guessing.
- **Unique per estate, not globally.** `wp_unique_post_slug()` is unique per site
  because slugs *are* routes on a site. Here the route is `/api/v1/media/{id}` —
  the id is the key — so the slug is a label, and two estates may legitimately both
  hold `logo`. The index is `(tenant_id, slug)`.
- **The suffix starts at 2.** `pixel`, `pixel-2`, `pixel-3` — exactly what
  `wp_unique_post_slug()` does. After 99 collisions a six-character ULID tail is
  appended instead of walking an unbounded loop on a hostile name.
- **The display name keeps its case.** `post_title` is not lowercased and neither
  is `filename` now; only the slug is. The extension is still forced to the sniffed
  one, so a title cannot claim a type the bytes do not have.
- **Nullable, with a reader fallback, and no backfill.** Every pre-existing row has
  no slug. Backfilling means inventing uniqueness across rows that never had any,
  and a wrong guess is worse than a documented fallback: `MediaController::slugOf()`
  derives the old value for those rows and reads the column for every new one.
- **The unique index is the authority; the computed slug is a guess.** Two uploads
  can compute the same first-free slug in the same instant. The index refuses the
  loser, `insertRow()` recomputes — now seeing the winner's row — and retries, up
  to three times, after which the driver's error is surfaced rather than swallowed.
  The bytes are unaffected: the object path is a ULID chosen before the row is
  written, so a retry cannot orphan or rename a file.
- **No plain `slug` index.** The only lookup is `(tenant_id, slug)`, which the
  composite unique already covers; a second index would only cost writes. Both the
  column and the index are existence-guarded, so the migration replays.

### What this discharges

§162.7 deferred "Delegating `FileUploadService` to `FileStore`" so the media
library's tested behaviour was not bundled into the visibility change. That
delegation landed in the same change as this section: `FileUploadService` takes an
optional `FileVisibilityStoreInterface` and, when the host binds one, writes both
the bytes and the row through it — one id scheme, one path convention, one
checksum, one place that knows what a stored file is. The hand-written path stays
for hosts that bind only the upload service, because `nvoos/laravel-adapter` is
consumed outside this repository.

The migration only adds a nullable column and its index; it does not read or
rewrite a row.

## 162.9 Generated media becomes a stored file

### The gap, with evidence

`generate_openai_image` calls the provider and returns what it said:

```php
$images[] = array( 'url' => ..., 'b64_json' => ..., 'revised_prompt' => ... );
return $this->success( 'Image(s) generated successfully.', ... );
```

The canonical WordPress tool with the same slug does one more thing. It calls
`wp_upload_bits()`, `wp_insert_attachment()`, `wp_generate_attachment_metadata()`,
writes `_wp_mcp_ai_openai_image_meta`, and returns `attachment_id`, `source_url`
and `file_name` alongside the provider payload
(`includes/tools/class-wp-mcp-ai-tool-generate-openai-image.php` →
`store_image_attachment()`).

So on this runtime a generated image had no id, no owner, no visibility and no
slug: it never appeared on `/admin/media` or `/api/v1/media`, and a caller who
wanted it later had to keep a provider URL that expires. Every image, video and
music tool in the manifest had the same shape. This is a **tool-contract gap**,
not a surface gap, and §162 is what makes closing it possible.

### The mechanism

One collaborator, `Nvoos\Core\Application\Media\GeneratedMediaPersister`, so the
logic exists once rather than once per tool. It takes the provider's entries and:

1. reads `b64_json`, refusing an entry that has none with a reason;
2. decodes it, refusing malformed base64 with a reason;
3. writes a temp file and hands the **path** to
   `FileVisibilityStoreInterface::storeWithVisibility()`, passing the owner,
   the estate and the visibility from the execution context;
4. removes the temp file in `finally`, and returns
   `['stored' => [...], 'failed' => [...]]`.

Three rules make it safe in front of a paid call:

- **Bytes only.** It never fetches the provider's temporary URL. A tool that
  intends to keep the bytes asks the provider for `b64_json`
  (`response_format` is overridden for that call only) and returns the store's
  stable URL instead. No second network hop, no SSRF surface, no dependency on
  a link's TTL.
- **Never throw.** A generation that succeeded is not reported as failed
  because a disk was full. Refusals and storage errors land in `media_failed`
  keyed by item, next to the bytes that were still returned.
- **The store decides the type.** The MIME hint is a hint; the registry sniffs
  the bytes and applies its allowlist and size caps (§162.7). This class does
  not restate that policy, so the two cannot drift.

### Parity rules adopted from WordPress

| WordPress behaviour | Here |
|---|---|
| always saves the image as an attachment | `save_to_media` defaults to `true` **when the host binds a registry** |
| stem from `file_name`, else `openai-image` | same |
| name `{stem}-{Ymd-His}`; extension from the format | same, except the extension is the store's, because the bytes decide it |
| `openai-image-{job_id}` when the context carries a job | same, from `context['parent_job_id']` |
| returns `attachment_id`, `source_url`, `file_name` | `media[]` entries carry `attachment_id`, `source_url`, `slug`, `filename`, `mime_type`, `size_bytes`, `visibility` |

One deliberate extension: a `visibility` argument (`public` by default), because
the file layer's whole point is that the caller can choose. Defaulting to
`public` keeps the WordPress-visible behaviour.

### Standards applied

- **OWASP File Upload Cheat Sheet** (already §162.3): validate the type from the
  bytes rather than trusting a header; application-generated filenames; size
  limits. All three are the store's job and are inherited here by construction.
- **Mutable names are not identities.** The store keys objects by ULID and rows
  by id; the display name advances with `-2`, `-3` and never addresses anything.
  A retried call therefore cannot overwrite an earlier generation.
- **Idempotency.** A retry still produces a second row: bytes are unique per
  call and the store does not dedupe across estates (§162.7). Deduplicating a
  re-run is a cost feature, not a correctness one, and is left out on purpose.

### Implementation plan

| Slice | Work | Gate |
|---|---|---|
| 1 | `GeneratedMediaPersister` + `generate_openai_image` (`save_to_media`, `file_name`, `visibility`) | `ImageAndFileToolsTest` (bytes reach the store, refusal keeps the image, opt-out stores nothing) |
| 2 | the other image generators: `generate_gemini_image`, `generate_cloudflareai_image`, `generate_higgsfield_image`, `create_image_variation`, `edit_openai_image`, `edit_gemini_image` | one probe each, same three assertions |
| 3 | video: `generate_veo_video`, `generate_sora_video`, `generate_omni_video`, `generate_higgsfield_video` | as above, plus the 206 follow-up below |
| 4 | audio/music: `generate_music`, `generate_openai_speech`, `transcribe_openai_audio` | as above |
| 5 | documents: `generate_document`-class tools and Paper Store artifact creation | as above |

**Named follow-up for slice 3:** a stored video is streamable only from a
private route that answers `Range` with `206 Partial Content` (RFC 9110
§15.3.7); serving whole bodies makes browser playback re-download from byte
zero on every seek. That is the §162.7 deferral and it is now on the critical
path for video toolkits rather than a nicety.

### 162.9.1 Slice 2: the other image generators

Five tools now persist through the same collaborator, and the two `_validated`
subclasses (`generate_gemini_image_validated`, `edit_gemini_image_validated`)
inherit it because they only override slugs and labels:

| Tool | Payload shape | Fallback stem |
|---|---|---|
| `create_image_variation` | `data[].b64_json` | `openai-variation` |
| `edit_openai_image` | `data[].b64_json` | `openai-edited-image` |
| `generate_gemini_image` | `predictions[].bytesBase64Encoded` | `gemini-image` |
| `edit_gemini_image` | `predictions[].bytesBase64Encoded` | `gemini-edited-image` |
| `generate_cloudflareai_image` | `result.image` (one string) | `cloudflare-image` |

Three things were factored out rather than copied five times:

- **Two dialects, one reader.** `GeneratedMediaPersister` reads `b64_json`
  (OpenAI's images API) or `bytesBase64Encoded` (Imagen via `:predict`). Putting
  the normalisation in the collaborator keeps every tool's `execute()` free of
  a translation step, and there is exactly one place to teach a third dialect.
- **One parameter descriptor.** `parameters()` returns the `save_to_media`,
  `file_name` and `visibility` schema fragments, and each tool merges them with
  `+`. Five hand-written copies would have drifted on what `save_to_media`
  promises within a release.
- **One naming rule.** `displayName()` implements the WordPress rule once:
  `{prefix}-{job_id}` from `context['parent_job_id']`, else
  `{file_name|prefix}-{Ymd-His}`.

Cloudflare needed one call-site adaptation rather than a persister change: it
answers with a single base64 string, so the tool wraps it as
`array(array('b64_json' => $image))` — the same shape every other provider
produces — instead of the persister growing a special case for a list that is
sometimes not a list.

**Deferred, with the reason recorded.** `generate_higgsfield_image` and
`generate_higgsfield_video` submit an asynchronous job and return
`request_id`/`status_url`; there are no bytes at that point. Persisting belongs
to `check_higgsfield_request`, which learns whether the job produced an output
and where it is — a different slice, and one that must decide what to do when a
completed job's bytes are already gone. Recording it here so its absence from
the table above reads as a decision rather than an oversight.

**Test seam.** `ImageAndFileToolsTest::setUp()` now binds a recording
`FileVisibilityStoreInterface`. Without it, every existing provider probe would
write a real object into the media disk through the newly defaulted
`save_to_media`; with it, the probes stay hermetic and the five new tests assert
on what the store was handed.

### 162.9.2 What this does not yet unlock

Storing generated media is necessary but not sufficient. The gap that remains is
the **link from a stored file into content**: `save_post` takes `post_id`,
`post_type`, `title`, `content` and taxonomy fields, and has no featured-image or
inline-attachment parameter. So an agent can now generate an image, find it with
`search_attachments`, and cite it by id — but cannot set it as a post's thumbnail
or insert it into a post body. On WordPress that link is
`set_post_thumbnail()`; here it is the next slice, and it is what makes the
library useful rather than merely populated.

### 162.9.3 The link into content: a featured image

§162.9.2 named the gap: an agent could store and find an image but not attach it
to anything. `save_post` now takes `featured_image_id`, on both of its
implementations (`save_post` and `save_post_validated`).

**What WordPress does, and what was copied.** `set_post_thumbnail()` writes
`_thumbnail_id` post meta and refuses an attachment that cannot produce an image
(`wp_get_attachment_image()` returns false → the meta is deleted). The tool
around it checks `wp_attachment_is_image()` first. Both halves are mirrored:

- the value lives in the content item's **meta**, the closest equivalent of post
  meta, so `get_post` returns it and the store's WP-shaped `metaQuery` can read
  `meta->featured_image_id`;
- the id is validated **at write time** against the registry — an unknown id is
  `404`, a non-image is `422`. A refused write leaves the post untouched rather
  than storing an id that can never render.

**Absent is not zero.** `featured_image_id: 0` clears the image; omitting the
argument leaves the current one alone. Conflating them would make any unrelated
post update silently drop the thumbnail, which is the kind of bug that only
shows up as "the images disappeared after the nightly import".

**One rule, two tools.** `save_post` and `save_post_validated` are separate
implementations, so the rule lives in `Nvoos\Core\Application\Media\FeaturedImage`
and both call it. The resolver returns the meta fragment, `null` for "argument
absent", and throws `ValidationException`/`NotFoundException` — exceptions both
tools already map to their error envelopes.

**Deleting the file later leaves the id.** That is what WordPress does with a
`_thumbnail_id` whose attachment is gone, and inventing a cascade here would make
`delete_file` write to content rows it does not own. Recorded so a reader does not
mistake it for an oversight; readers must tolerate an id whose file is missing.

### 162.9.4 Transforms persist, chain, and stop being sideways

The four transform tools (`resize_image`, `crop_image`, `rotate_image`,
`convert_image_format`) returned `{width, height, mime_type, bytes}` — where
`bytes` is a **byte count** — plus an output path in the worker's scratch
directory. Nothing addressable came out, so `generate → resize` meant fetching
the generated bytes and re-uploading them.

Two changes close that:

- **`file_id` as the source.** The image port takes a *local path* — the adapter's
  own docblock records that `wp_get_image_editor()` only accepts a path and the
  tools pass `image_url` through, so a URL fails the same way in both runtimes.
  A stored file already has a path, so `file_id` is the only primitive that can
  chain; `getPath()` resolves it and `image_url` stays for callers who really do
  have a path.
- **The output is stored.** `GeneratedMediaPersister` gained `storeFile()` and
  `attachFile()`: a transform hands over the path the processor already wrote, so
  the bytes are never encoded to base64 and decoded again. The same three rules
  apply as for generations — the store sniffs the type, a refusal becomes
  `media_failed`, and `save_to_media` defaults to true when a registry is bound.

**A bug found on the way.** The media worker's `POST /api/image/transform`
pipeline never called `sharp().rotate()` before applying geometry. Sharp does not
auto-orient implicitly, so a phone photo whose orientation lives only in the EXIF
tag was resized against the stored pixel grid — and the tag is dropped on
re-encode, so nothing downstream could tell the result was wrong. The pipeline now
auto-orients first (`applyTransformOperations()`), which is a no-op for an upright
image. `image.transform.test.js` pins it with a 4×2 image tagged orientation 6,
which must resize to 2×4 rather than 2×1.

*Validation note:* the media-worker tests need `node_modules`, which this
checkout does not have, so that assertion is covered by CI rather than locally.
The PHP side was run: `ContentAndCrawlerToolsTest` + `ImageProcessingAdapterTest`
(26 tests), the readiness guards (21), and the adapter suite (348).

### 162.9.5 Images in the body

`featured_image_id` (§162.9.3) answers "what represents this post". It does not
answer "what is in it". WordPress's `create_post` takes a `content_images` array
and renders each entry as an image block
(`trait-wp-mcp-ai-tool-content-media.php`); this runtime now accepts the same
argument on `create_post` and `create_post_validated`.

**The argument, copied exactly.** `{source, alt, caption, position}` with
`source` a stored file id or an absolute URL, `position` one of
`start|middle|end` (default `middle`), and a cap of five. `middle` means "after
the paragraph at the midpoint of the body", which is what the WordPress trait
does.

**Two deliberate departures, both because copying would be wrong here.**

- **Attributes are written into the markup.** WordPress emits
  `<figure class="wp-block-image"><img class="wp-image-12" ...>`, then relies on
  `wp_filter_content_tags()` to add `srcset`, `sizes`, `loading` and the
  intrinsic size at render time, keyed off that class. This runtime has no render
  filter, so the block carries `width`, `height`, `loading="lazy"` and
  `decoding="async"` itself. Dimensions come from `getimagesize()` on the stored
  bytes and are omitted when they cannot be read — a missing attribute is a
  missed optimisation, a guessed one is a distorted image. web.dev's image
  guidance is explicit that every `<img>` should carry `width` and `height` so
  the browser can reserve space and avoid layout shift.
- **A private file is refused** (`422`). WordPress has a single media
  visibility; here a private file deliberately has no public URL, so embedding
  it would ship an `<img>` that returns 401 for every anonymous reader. A broken
  image is worse than an error the caller can act on.

**Escaping.** `alt` and the caption are escaped with `ENT_QUOTES`; the caption is
`strip_tags()`-ed first, because it arrives from a model and an image block is
not a place to accept HTML. `source` strings are restricted to absolute
`http(s)` or a site-relative path — `javascript:` and `data:` are rejected — which
is the equivalent of WordPress's `esc_url()` protocol allowlist.

**Not ported: `content_charts`.** The WordPress trait renders charts by emitting
`<script src=".../chart.min.js">` plus an inline `<script>` into post content.
That is a stored-XSS shape and a CSP problem, and this runtime already has chart
fences and `create_chart` as the supported path. Declining it is a decision, not
