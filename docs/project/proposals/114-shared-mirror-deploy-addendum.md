# Proposal 114 addendum — shared-mirror deploy for forged sites (branch per site)

> Owner decision 2026-11-06: forged client sites deploy through **one shared
> private mirror repo** (`nvdigitalsolutions/nvoos-forge-sites`) with **one
> branch per site** — no per-site source repos, nothing generated committed
> to the monorepo. Velocity apps connect to the mirror, select their branch,
> and serve the branch root.

## Why this shape (research, 2026-11-06)

- **Cloudways Velocity supports it natively.** The official Velocity docs
  confirm per-app **Branch** ("the Git branch used for deployment") and
  **Root Directory** ("the folder where your application code is located")
  settings, and repo connections from GitHub/GitLab/Bitbucket with framework
  auto-detection. Sources: *How to Manage Deployments for your Cloudways
  Velocity Application* and *Cloudways Velocity Application Overview Guide*
  (support.cloudways.com articles 16187473 / 15550860), velocity.php
  (cloudways.com).
- **Never commit build output to the source repo.** The industry-standard
  static deploy (GitHub Pages + Actions; Hugo/Astro/React guides) builds
  fresh in CI and publishes only the build: the `gh-pages` force-push
  pattern (`peaceiris/actions-gh-pages`, `git push --force origin
  gh-pages:gh-pages`) is the canonical form. This is exactly the forge's
  existing invariant ("built assets never ship") and the 092 mirror
  precedent ("flat history, force-pushed").
- **One branch per deploy target is an established pattern.** Per-branch
  deploy surfaces (Pages branch sources, `git subtree split --prefix …
  -b gh-pages`, bare-repo + post-receive checkout) all express the same
  idea: the deploy branch is a *product* of CI, not a workspace. Applying
  it per client site (branch = site) keeps each site's history flat and
  its content at the branch root — which is what Velocity's Root directory
  serves.
- **Serialize deploys with a concurrency group.** Force-pushed branches
  must not race: the workflow pins `concurrency: group: forge-sites,
  cancel-in-progress: false` (the standard `deploy-${{ github.ref }}`
  discipline from GitHub Actions deployment guides).
- **Secrets stay out of everything committed.** Mirror auth is a
  repo-scoped deploy token in monorepo secrets (`NVOOS_FORGE_MIRROR_TOKEN`);
  the mirror repo itself carries no credentials; profiles carry none.

## The model

```
nvdigitalsolutions/nvoos-forge-sites        (PRIVATE mirror — never commit directly)
├── main                      README only (the clone anchor for mirror-push)
├── site/jayainc              jayainc.com  dist/ at branch root (force-pushed, flat)
└── site/<client>             one branch per client

mcp-ai-wpoos (public monorepo)
├── examples/nvoos-astro-forge/sites/<name>.json   the ONLY committed artifact per site
└── .github/workflows/forge-sites.yml              rebuild + mirror pipeline
```

Velocity app wiring per site: connect `nvoos-forge-sites`, **Branch** =
`site/<name>`, **Root directory** = repo root (static app, no Node
runtime needed — the branch is plain `dist/` output).

## Forge changes (shipped with this addendum)

- `lib/deploy-config.ts` — `DeployConfig.mirrorRepo` + `.siteBranch`
  (set together; half-set configs throw). Velocity mode gains the
  branch-per-site shape: `deploy.yml` calls the emitted
  `scripts/mirror-push.mjs` instead of the legacy `deploy`-branch/`site/`
  folder steps. `mirrorPushScript()` is the single template — the workflow
  and the CLI run the same emitted file, so they cannot drift.
- `scripts/forge.mjs` — `deploy`/`deploy-config` gain
  `--mirror-repo <owner/repo>` + `--site-branch <branch>` (validated:
  pairing, shape). `deploy --mirror-repo …` skips repo creation and
  mirrors a prebuilt `dist/` directly (operator staging path); without
  `dist/` it prints the build instructions instead.
- `.github/workflows/forge-sites.yml` — the monorepo pipeline: push
  (sites/templates/libs) + `workflow_dispatch` (optional `site`) +
  `repository_dispatch` `nvoos-forge-content-changed` (HMAC verified by the
  committed `.github/forge/verify-dispatch.mjs` — generated by
  `emitDeployConfig`, provenance header). Per site: scaffold →
  deploy-config (velocity mirror) → `npm install` + `ASTRO_SITE` build →
  mirror-push. Unset mirror secrets degrade to build-only.
- `sites/README.md` — the profile/branch/Velocity convention.

## Runbook state (2026-11-06)

- Mirror repo created (private) and `site/jayainc` branch seeded.
- Repo variable to set on the monorepo: `NVOOS_FORGE_MIRROR_REPO` =
  `nvdigitalsolutions/nvoos-forge-sites`.
- Repo secrets to set on the monorepo: `NVOOS_FORGE_MIRROR_URL`,
  `NVOOS_FORGE_MIRROR_TOKEN` (repo-scoped deploy token on the mirror),
  `FORGE_WEBHOOK_SECRET` (shared with `nvoos-forge-bridge` on client WPs).
- Velocity: create a static app, connect the mirror repo, Branch =
  `site/jayainc`, Root directory = repo root; point the domain/DNS when
  ready to review.
- First mirror push: run `forge-sites.yml` via `workflow_dispatch` (after
  secrets exist) or locally:
  `node scripts/forge.mjs deploy sites/jayainc.json --target ./jayainc-frontend --to velocity --mirror-repo nvdigitalsolutions/nvoos-forge-sites --site-branch site/jayainc`
  with `GITHUB_TOKEN` set and `dist/` built.
