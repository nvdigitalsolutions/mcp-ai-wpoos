# Implementation Plan: Research & Semantic Tool Reliability (Multi-Provider)

**Status:** Implemented (uncommitted, working tree) — see §Implemented below
**Scope:** `includes/tools/`, `includes/services/embedding/`, `includes/class-wp-mcp-ai-tool-registry.php`, `includes/toolkit-metadata-mapping.php`, `includes/class-wp-mcp-ai-default-assistants.php`, `includes/helpers/class-wp-mcp-ai-tool-presets-helper.php`, tests, docs, `.agents/skills/`
**Goal:** Make `semantic_content_search` and `deep_research` work for *any* assistant/provider combination, degrade gracefully instead of dying, and close the taxonomy-discovery gap with new read-only tools.

## 0. Verified problem statement

Field reports from the `nv-oos-nugl-garden-agent` assistant (DeepSeek-backed,
no OpenAI key configured on the site):

| # | Symptom | Root cause (verified in code) |
|---|---------|------------------------------|
| 1 | `semantic_content_search` → `McpError: No OpenAI API key has been configured.` | `WP_MCP_AI_Tool_Semantic_Content_Search::generate_query_embedding()` only understands `gemini`/`google` vs. "everything else". Assistant provider is `deepseek` → falls to OpenAI embeddings → no key → hard `WP_Error`. It ignores the existing multi-provider abstraction `WP_MCP_AI_Vector_Context_Service::get_embedding_provider()` (OpenAI / Ollama / DigitalOcean + `embedding_provider` setting + `wp_mcp_ai_embedding_provider` filter) that `search_content` already uses. |
| 2 | `deep_research` returns `report: ""`, `word_count: 0` while sources/queries are populated | `analyze_findings()` checks `isset( $result['choices'][0]['message']['content'] )` — an **empty string passes `isset()`**, so an empty completion silently becomes a "successful" report. DeepSeek reasoning models are known to return CoT in `reasoning_content` with empty `content` (Stack Overflow #79654244), and `finish_reason: "length"` truncation also yields empty/partial content. No retry, no non-empty validation, no `reasoning_content` fallback, no `finish_reason` inspection. Worse: `execute()` **caches the empty report for 1 hour** (`WP_MCP_AI_Cache_Helper::set()`), poisoning the cache. |
| 3 | No taxonomy-listing tool | Only `create_term` / `update_term` exist. Agents cannot discover the site's category/tag structure to map new posts against. |
| 4 | Silent 0-score results on provider switch | `semantic_content_search` compares query vectors against stored `_wp_mcp_ai_embeddings` post meta with **no model/dimension check**; `calculate_cosine_similarity()` returns `0.0` when dimensions differ. A site whose posts were embedded with OpenAI (1536-dim) and is queried via Ollama (768-dim) gets "0 results" with no explanation. |
| 5 | Two parallel embedding stores | `semantic_content_search`/`batch_embed_content` use post meta `_wp_mcp_ai_embeddings`; `search_content` (semantic/hybrid) uses `WP_MCP_AI_Content_Embedding_Store` (custom table, keyed by `provider_id + model` — dimension-safe). Same feature, two indexes. |

## Research basis (best practices applied)

- **Provider abstraction + fallback chain** — embedd the provider decision behind an interface and fall back down a configured chain instead of hard-coding one vendor. (Hugging Face blog "Simple RAG Retrieve Tools": "architectural separation between indexing and retrieval phases … embedding flexibility across multiple providers (OpenAI, Cohere, HuggingFace)"; DEV Community "Multi-Provider Fallback for Local RAG": strict hierarchy with automatic switch.)
- **Degrade to keyword, not to failure** — "Vector database outages should trigger fallback to keyword search rather than complete service failure. Embedding API outages can use cached embeddings for known queries." (Introl "RAG Infrastructure" production guide.) This is *already the in-repo pattern*: `search_content` falls through to keyword search when embedding classes are unavailable.
- **Decouple embeddings from the chat provider** — an assistant's LLM provider (DeepSeek) must not dictate the embedding backend; embedding provider is an independent setting. (Hugging Face blog, Reddit r/Rag "Embeddings in Multi-LLM RAG Workflows".)
- **Dimension/model-keyed storage** — cosine similarity is only defined between vectors of equal dimension generated by compatible models; store vectors keyed by `provider + model`. (GoPenAI "Picking the Right Embedding Model…", Reddit r/Rag.) In-repo precedent: `WP_MCP_AI_Content_Embedding_Store`.
- **Validate non-empty output; reject or retry `finish_reason: length`** — "Reject or retry finish_reason: 'length' when complete output is required. Validate that content is non-empty before parsing it." (chat-deep.ai "DeepSeek Thinking Mode: Live API Tests".) DeepSeek official docs confirm content may be cut off on `length`.
- **Bounded retry + model fallback chain** — retry transient empties a small number of times, then switch model/provider; reject output after two failures to avoid cascading errors. (liteLLM "Reliability — Retries, Fallbacks"; DevToolKit.cloud "LLM API Integration Patterns (2026)"; Medium "Error Handling & Retries".)
- **Never cache failure shapes** — a cache write of an empty report turns a transient failure into a persistent one for the TTL window. (General cache-hygiene; verified bug in §0 row 2.)

## WS-1 — Unified multi-provider embedding resolution for `semantic_content_search`

**Why:** Row 1/4/5. The tool must stop depending on the assistant's chat
provider and route through the existing embedding-provider abstraction,
extended with Gemini.

**Files:**
- `includes/services/embedding/class-wp-mcp-ai-embedding-provider-gemini.php` (new)
- `includes/services/class-wp-mcp-ai-vector-context-service.php`
- `includes/tools/class-wp-mcp-ai-tool-semantic-content-search.php`
- `tests/test-mempalace-phase3-embedding-providers.php` (extend)

**Steps:**

1. **New `WP_MCP_AI_Embedding_Provider_Gemini`** implementing
   `WP_MCP_AI_Embedding_Provider_Interface`, wrapping
   `WP_MCP_AI_Gemini_Client::create_embedding()`:
   - `get_id()` → `'gemini'`; `get_model()` → `gemini-embedding-001`
     (client default; do **not** reuse the stale `text-embedding-004` label
     the tool currently returns).
   - `is_available()` → `gemini_api_key` configured + client class exists.
   - `embed()` → call with `task_type: RETRIEVAL_QUERY`, return
     `embedding.values` as `float[]` (same shape contract as the other
     providers).
   - Load it in `WP_MCP_AI_Vector_Context_Service::ensure_provider_classes_loaded()`.
2. **Extend `resolve_default_provider()`**: accept `'gemini'` in the
   `embedding_provider` preference and add Gemini to the auto-detect chain
   (proposal: OpenAI → Ollama → Gemini → DigitalOcean — order debate below).
3. **Rewrite `generate_query_embedding()`** in the semantic search tool to:
   - Prefer Gemini **only when the assistant is Gemini-backed AND Gemini is
     available** (preserves today's intent).
   - Otherwise delegate to
     `WP_MCP_AI_Vector_Context_Service::get_instance()->get_embedding_provider()`
     and `embed( $query )` — honouring the explicit `embedding_provider`
     setting, the `wp_mcp_ai_embedding_provider` filter, and the auto-detect
     chain. Drop the hard OpenAI default.
   - Return `{ embedding, model, provider_id }` from the provider object.
   - On `WP_Error`, return an **actionable** error:
     `wp_mcp_ai_no_embedding_provider` with `data.actions` listing the three
     fixes (add OpenAI key / Gemini key / Ollama endpoint, or set
     `embedding_provider`) — never the misleading
     "No OpenAI API key has been configured" when the assistant is DeepSeek.
4. **Vector-store search guard:** the OpenAI vector-store branch is
   OpenAI-only by design. Keep it, but treat a missing-key `WP_Error` as
   *skipped* (logged, `vector_store_search: false` in output) instead of
   letting it fail the whole tool.

**Acceptance:**
- DeepSeek assistant + only Gemini key → local semantic search works via Gemini embeddings; response includes `query_embedding_provider: "gemini"`.
- No embedding provider at all → tool returns the actionable `WP_Error` (not an OpenAI-key message).
- `embedding_provider: "ollama"` + Ollama endpoint → Ollama used regardless of assistant provider.
- Existing OpenAI-only installs: byte-for-byte behaviour unchanged (regression).

## WS-2 — Graceful degradation & vector hygiene in `semantic_content_search`

**Why:** Rows 3–5 and the Introl best practice (keyword fallback beats
service failure). Also fixes the silent 0-score trap.

**Files:**
- `includes/tools/class-wp-mcp-ai-tool-semantic-content-search.php`

**Steps:**

1. **Keyword fallback:** when embedding resolution/embedding fails (and no
   vector-store results exist), do **not** fail the tool — run a keyword
   search over the same `post_types` corpus (WP_Query `s` + optional taxonomy
   filters), and return:
   ```php
   array(
       'success'                 => true,
       'fallback_mode'           => 'keyword',
       'semantic_search_enabled' => false,
       'warning'                 => /* why semantic was unavailable + how to fix */,
       'results'                 => $keyword_results,
       ...
   )
   ```
   Canonical-envelope compliant (success array, no `success => false`).
   Only return `WP_Error` when *both* semantic and keyword paths fail.
   Include `keyword` results shaped like existing results with
   `similarity_score: null` / `source: "wordpress_keyword"`.
2. **Dimension-mismatch hygiene:** while scoring stored post-meta
   embeddings, skip vectors whose count differs from the query vector;
   track `skipped_dimension_mismatch`. If a post's stored meta carries a
   `model`/`provider` (some embed writers store it), prefer rows matching
   the query provider when available. Report
   `embeddings_checked`, `skipped_dimension_mismatch`, and
   `query_embedding_model` in the response so agents can see *why* results
   are sparse.
3. **Store convergence (follow-up, separate PR):** long-term, point
   `semantic_content_search` at `WP_MCP_AI_Content_Embedding_Store`
   (provider+model-keyed table) and deprecate `_wp_mcp_ai_embeddings` reads.
   Flagged as follow-up because it touches `batch_embed_content` /
   `create_text_embeddings` and migration tooling.
4. Add a `wp_mcp_ai_semantic_search_keyword_fallback` filter (default on)
   so ops can force hard failure if they prefer.

**Acceptance:**
- Semantic unavailable → keyword results returned with explicit `warning`; agent can still scan the archive.
- Mixed-dimension corpus → mismatched rows skipped, counters populated, no silent zeros.
- Threshold semantics documented in tool description (`threshold` applies to semantic results only).

## WS-3 — `deep_research` completion validation, retry & provider fallback

**Why:** Row 2 — empty report, cache poisoning, reasoning-model behaviour.

**Files:**
- `includes/tools/class-wp-mcp-ai-tool-deep-research.php`
- `tests/test-tool-deep-research.php` (new)

**Steps:**

1. **Validate non-empty content** in `analyze_findings()`: trim the content;
   treat empty string as failure, not success.
2. **Reasoning-content fallback:** if `content` is empty but the normalized
   response carries non-empty `reasoning_content` (DeepSeek passes it
   through), use it and set `analysis['used_reasoning_fallback'] = true`
   (logged as a warning event). This mirrors DeepSeek's documented
   CoT-output behaviour.
3. **`finish_reason` inspection:** if `finish_reason === 'length'`, retry
   once with the next-larger `max_tokens` bucket for the depth (e.g.
   standard 2000 → 4000) before falling back; if still truncated, return
   `WP_Error( 'wp_mcp_ai_report_truncated', ... )` whose `data` includes the
   collected `sources`, `queries_used`, and a hint to reduce `depth`.
4. **Bounded retry + provider fallback chain:** refactor `get_ai_setup()` to
   expose the *ordered list* of available provider setups (existing chain:
   OpenAI → Gemini → Anthropic → Cloudflare → HuggingFace → Ollama →
   DeepSeek → OpenRouter → …). On empty/truncated content: retry the same
   provider once, then walk the chain (max **2 total attempts** per the
   "reject after two failures" guidance), logging each hop. On the final
   failure return `WP_Error` with `data.sources` etc. so the agent gets the
   salvageable material instead of an empty string.
5. **Cache-poisoning guard in `execute()`:** skip
   `WP_MCP_AI_Cache_Helper::set()` whenever
   `str_word_count( $research_report['report'] ) === 0`.
6. **Report shape:** on success add `used_reasoning_fallback` /
   `attempts` to the report metadata (non-breaking).

**Acceptance:**
- DeepSeek returning reasoning-only/empty content → tool either produces a real report (fallback/retry) or a `WP_Error` containing the 6 sources — never `report: ""` with `word_count: 0`.
- Empty reports are never cached; a successful retry repopulates correctly.
- DeepSeek `finish_reason: length` → single larger-budget retry, then explicit truncation error.
- OpenAI path: unchanged for healthy completions (regression).

## WS-4 — New read-only taxonomy tools: `list_terms` + `list_taxonomies`

**Why:** Row 3. Agents need to *discover* the taxonomy structure before
`create_term`/`update_term` mapping.

**Files:**
- `includes/tools/class-wp-mcp-ai-tool-list-terms.php` (new)
- `includes/tools/class-wp-mcp-ai-tool-list-taxonomies.php` (new)
- `includes/class-wp-mcp-ai-tool-registry.php` (`load_default_tools` + `get_tool_group_map` → `wordpress-core`)
- `includes/toolkit-metadata-mapping.php` (entries: `content_publishing`, `pattern_compatibility: ['orchestrator', 'peer_to_peer']`, `profession_tags: ['content_strategist','seo_specialist']`, `risk_level: 'info'`)
- `includes/class-wp-mcp-ai-default-assistants.php` + `includes/helpers/class-wp-mcp-ai-tool-presets-helper.php` (add slugs next to `create_term`/`update_term`)
- `docs/reference/tools/tool-reference.md`, `includes/tools/README.md`
- `tests/test-tool-list-terms.php`, `tests/test-tool-list-taxonomies.php` (new)

**`list_terms` design** (modelled on `create_term` conventions — canonical
envelope, two-gate sanitisation, `WP_MCP_AI_Tool_Chat_Response`):
- Params: `taxonomy` (required, `sanitize_key`), `search` (optional),
  `hide_empty` (bool, default false), `parent` (int, optional),
  `limit` (default 50, max 500), `offset` (default 0),
  `orderby` (enum `name|count|slug|term_id`, default `name`),
  `order` (enum `ASC|DESC`, default `ASC`), `include_counts` (bool, default true).
- Capability: `read` (read-only listing; no `manage_terms` needed).
- Returns per term: `term_id, name, slug, description, parent, count,
  taxonomy, link` (via `get_term_link()` where public).
- Capability flags: `read-only`, `local-only`.
- Degenerate cases: invalid taxonomy → `WP_Error` naming valid taxonomies in
  `data`.

**`list_taxonomies` design:**
- Params: `public` (bool|null default null = all), `object_type` (optional).
- Returns registered taxonomies: `name, label, hierarchical, public, rest_base,
  object_types, show_ui`.
- Capability: `read`; flags: `read-only`, `local-only`.

**Acceptance:**
- `list_terms { taxonomy: "category" }` returns the site category tree (id/name/parent/count) — closing the reported gap.
- Both tools appear in `tools/list` for assistants with them assigned; base-version registration works.
- Unit tests cover: listing, search filter, pagination, invalid taxonomy, capability gate.

## Open questions / decisions needed

1. **Auto-detect order** in `resolve_default_provider()` — proposal
   OpenAI → Ollama → Gemini → DigitalOcean. Gemini before Ollama? Dimension
   stability favours whichever provider originally embedded the corpus —
   prefer explicit `embedding_provider` setting whenever set (already the case).
2. **Store convergence timing** (WS-2 step 3) — do we accept
   `_wp_mcp_ai_embeddings` as legacy-read for one more release while
   `Content_Embedding_Store` becomes the write path?
3. **Keyword-fallback threshold semantics** — keyword results have no
   similarity score; return `null` score vs. omit field?
4. **`list_terms` shape** — include hierarchical tree helper (children ids)
   or flat list only? Proposal: flat list + `parent` field; agents can
   assemble the tree.
