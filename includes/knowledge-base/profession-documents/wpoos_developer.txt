WP oOS Developer - Professional Knowledge Base

=== OVERVIEW ===

WP oOS (WordPress Open Operator System) is an enterprise-grade WordPress plugin that provides a comprehensive AI Assistant framework. It integrates OpenAI GPT models, Google Gemini, and Ollama (local AI) through the Model Context Protocol (MCP), offering 65+ built-in tools for content management, media generation, e-commerce, forms, and system automation.

=== ARCHITECTURE ===

Core Components:
1. Profession System (Custom Post Type)
   - Defines AI assistant specializations
   - Includes playbooks (structured instructions)
   - Contains knowledge bases for RAG (Retrieval Augmented Generation)
   - Specifies default tool sets
   
2. Assistant System (Custom Post Type)
   - Links to professions for configuration inheritance
   - Configures AI provider (OpenAI/Gemini/Ollama)
   - Sets model parameters (temperature, max_tokens, streaming)
   - Manages authentication credentials (bearer tokens)
   
3. Tool Registry
   - Central management of 65+ built-in tools
   - Extension system for custom tools
   - Capability-based access control
   - Structured parameter validation with Symfony Validator
   
4. REST API
   - MCP-compliant endpoints at /wp-json/mcp-ai/v1/
   - Server-Sent Events (SSE) for streaming responses
   - Multiple authentication methods (nonce, bearer, Auth0, guest)
   - Tool execution and assistant management

=== REST API ENDPOINTS ===

GET /wp-json/mcp-ai/v1/assistants
- List all available assistants
- Returns: ID, name, profession, model, provider, tools
- Authentication: WordPress nonce or bearer token

POST /wp-json/mcp-ai/v1/chat
- Send messages to assistant with streaming
- Parameters: assistant_id, message, stream (boolean)
- Returns: SSE stream or JSON response
- Authentication: WordPress nonce, bearer token, Auth0, or guest token

POST /wp-json/mcp-ai/v1/tools
- Execute tools directly without assistant context
- Parameters: tool_slug, arguments
- Returns: Tool execution result
- Authentication: WordPress nonce or bearer token

GET /wp-json/mcp-ai/v1/sse
- Server-Sent Events endpoint for streaming
- Used internally by chat endpoint
- Authentication: Same as chat endpoint

=== AUTHENTICATION METHODS ===

1. WordPress Nonce (Same-Origin):
   Header: X-WP-Nonce: abc123xyz
   Usage: Frontend JavaScript on same WordPress site
   Validity: 12-24 hours (WordPress default)
   
2. Bearer Token (Plugin-Issued):
   Header: Authorization: Bearer cred_xxxxx.SECRET
   Usage: Headless apps, external integrations
   Format: credential_slug.SECRET_KEY
   Generation: Settings → WP oOS → Authentication → Create Credential
   
3. Auth0 Token (Enterprise):
   Header: Authorization: Bearer <Auth0-JWT>
   Usage: Enterprise SSO integrations
   Configuration: Settings → WP oOS → Auth0 Settings
   
4. Guest Token (Public Chat):
   Header: X-WP-MCP-AI-Guest: temporary_token
   Usage: Public-facing chat surfaces without login
   Validity: Session-based, expires after 24 hours

=== PROFESSION STRUCTURE ===

Required Fields:
- title: Display name (e.g., "Software Developer")
- slug: Unique identifier (e.g., "software_developer")
- description: Brief summary of profession
- category: Classification (technical/creative/advisory/healthcare/financial/legal/other)
- role_description: AI system instructions for this role
- expertise: Array of knowledge areas
- warnings: Array of boundaries and restrictions
- default_tools: Array of tool slugs to enable

Optional Fields:
- knowledge_base: Markdown text for RAG
- memory_files: Attachment IDs for additional context
- supported_mime_types: Array of MIME types for file handling

Playbook Format:
- Stored in includes/knowledge-base/profession-playbooks/professions/
- Naming: [slug].txt
- Structure: 8 sections (role boundaries, intake, workflow, deliverables, quality, templates, examples, vocabulary)

=== ASSISTANT CONFIGURATION ===

Creation Methods:
1. Admin UI: Add Assistant page with form inputs
2. create_assistant tool: Programmatic creation via AI
3. Direct repository: WP_MCP_AI_Assistant_Repository

Key Settings:
- name: Assistant display name
- profession_id: Link to profession (inherits tools, playbooks, knowledge)
- provider: openai | gemini | ollama
- model: Provider-specific model name
- temperature: 0.1 (factual) to 2.0 (creative), default 0.7
- max_tokens: Response length limit (1000-128000)
- stream: Enable/disable streaming responses (recommended: true)
- tools: Array of tool slugs (inherits from profession if empty)
- system_instructions: Custom instructions (merged with profession playbooks)

Model Selection Guidelines:
- Factual/Technical: GPT-4o, temperature 0.1-0.3
- Creative Writing: GPT-4 Turbo, temperature 0.7-1.2
- Complex Reasoning: o1-preview, o1-mini (no temperature)
- Fast/Economical: Gemini 2.0 Flash, temperature 0.5-1.0
- Long Context: Gemini 1.5 Pro (1M tokens)
- Local/Private: Ollama (llama3, mistral)

=== CUSTOM TOOL DEVELOPMENT ===

File Location: includes/tools/class-wp-mcp-ai-tool-[slug].php

Required Methods:
1. get_slug(): Return unique tool identifier
2. get_definition(): Return tool metadata and JSON schema
3. execute($arguments, $context): Implement tool logic

Registration: Add to includes/tools/tools-init.php

Best Practices:
- Extend WP_MCP_AI_Tool_Base
- Validate all inputs (Symfony Validator)
- Check capabilities before execution
- Sanitize inputs (sanitize_text_field, absint)
- Escape outputs (esc_html, esc_url)
- Return array or WP_Error
- Write PHPUnit tests in tests/test-[tool].php
- Document in docs/tool-reference.md

=== STREAMING IMPLEMENTATION ===

Server-Side (PHP):
- Use WP_MCP_AI_Stream_Handler for SSE formatting
- Set Content-Type: text/event-stream
- Disable output buffering
- Send data: prefix for each chunk
- Send data: [DONE] to signal completion

Client-Side (JavaScript):
- Use fetch() with response.body.getReader()
- Parse SSE format (lines starting with "data: ")
- Handle [DONE] signal for completion
- Update UI progressively as chunks arrive
- Implement error handling and reconnection

Benefits:
- Real-time response rendering (better UX)
- Reduced perceived latency
- Early feedback on long responses
- Token-by-token display for transparency

=== SECURITY BEST PRACTICES ===

Input Validation:
- Use sanitize_text_field() for text inputs
- Use absint() for integer IDs
- Use esc_url() for URLs
- Use wp_kses_post() for HTML content
- Validate file uploads (MIME type, size, extension)

Output Escaping:
- Use esc_html() for text display
- Use esc_url() for link attributes
- Use esc_js() for JavaScript strings
- Use esc_attr() for HTML attributes
- Never echo unescaped user input

Capability Checks:
- Always check current_user_can() before privileged operations
- Common capabilities: edit_posts, manage_options, activate_plugins
- Tool definitions include required_capability field
- REST endpoints validate permissions

API Key Management:
- Store keys in WordPress options (wp_options table)
- Never commit keys to version control
- Use environment variables for production
- Rotate keys regularly
- Monitor usage and set quotas

Rate Limiting:
- Respect provider rate limits (OpenAI, Gemini)
- Implement exponential backoff for retries
- Cache results when possible
- Queue long-running tasks
- Monitor usage to prevent quota exhaustion

=== PERFORMANCE OPTIMIZATION ===

Caching Strategy:
1. Object Cache: WordPress transients for API responses
2. Page Cache: Full-page HTML caching for frontend
3. CDN Cache: Cloudflare/Varnish for static assets
4. Database: Query result caching with transients

Cache Management:
- Use purge_cache tool after content updates
- Implement cache warming for high-traffic content
- Set appropriate TTLs (Time To Live)
- Monitor cache hit rates
- Exclude admin areas from page caching

Streaming Benefits:
- Reduces Time to First Byte (TTFB)
- Progressive rendering improves perceived performance
- Lower memory usage on server
- Better UX for long responses

Background Processing:
- Use create_cron_job for deferred tasks
- Implement async mode for video generation
- Queue batch operations
- Monitor cron execution with list_cron_jobs

=== TROUBLESHOOTING ===

Assistant Not Responding:
- Check AI provider API key validity
- Verify assistant is published (not draft)
- Check user permissions and capabilities
- Review error logs for API failures
- Confirm model is available (not deprecated)

Tool Not Working:
- Verify tool is enabled for assistant
- Check required capability for tool
- Validate tool arguments match schema
- Review tool execution errors in logs
- Test tool in isolation via REST API

Streaming Issues:
- Verify stream parameter is true
- Check server output buffering settings
- Ensure proper SSE headers sent
- Test with curl to isolate client issues
- Review nginx/Apache SSE configuration

Authentication Failures:
- Verify nonce is fresh (not expired)
- Check bearer token format (cred_slug.SECRET)
- Confirm Auth0 configuration
- Test with different auth method
- Review authentication logs

Performance Problems:
- Enable caching (object, page, CDN)
- Reduce max_tokens if responses too long
- Use Gemini Flash for faster responses
- Implement async processing for heavy tasks
- Monitor database query performance
